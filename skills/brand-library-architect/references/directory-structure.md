# Directory structure

The canonical layout for a brand library produced by this skill. Read this *before* Phase 1 — knowing where files belong prevents misplacing them later.

## Top-level layout

```
{{REPO_ROOT}}/
├── README.md                ← repo front door (Phase 4)
├── CONTRIBUTING.md          ← contribution guide (Phase 4, OSS only)
├── SECURITY.md              ← vulnerability disclosure (Phase 4)
├── CODE_OF_CONDUCT.md       ← Contributor Covenant adopt-by-reference (Phase 4)
├── LICENSE                  ← project license file (already exists)
├── package.json / pyproject / etc. (already exists)
└── brand/                   ← brand library root
```

Repo conventions live at the repo root because that's where GitHub / GitLab / package managers expect them. The `brand/` directory contains everything else.

```
├── CLAUDE.md                ← directory-local guidance for AI agents (Phase 2)
├── RECIPES.md               ← common-task playbook (Phase 2)

├── TONE.md                  ← register guide (Phase 4)
├── PRICING.md               ← pricing argument (Phase 4, if paid)
├── icons/                   ← logo SVGs and PNG rasters
│   ├── svg/                 ← canonical vector source

│   │   ├── {{slug}}-mark-on-light.svg

│   │   └── {{slug}}-lockup-on-light.svg
│   └── png/                 ← high-res raster equivalents
│       ├── {{slug}}-mark.png
│       └── {{slug}}-mark-on-light.png
├── _source/                 ← brand asset sources (HTML, AI, future formats)
│   ├── html/                ← HTML source sheets (Phase 3)
│   │   ├── concept-{{name}}.html ← per-concept (system, identity, etc.)
│   │   ├── manifesto.html   ← portrait anti-card

│   │   ├── readme.html      ← README banner
│   │   ├── og.html          ← Open Graph image
│   │   ├── composite.html   ← composite reference sheets (optional)
│   │   └── _archive/        ← retired sheets preserved for reference
│   └── ai/                  ← Adobe Illustrator sources (.ai files; optional)
├── exports/                 ← rendered WebP outputs (generated by `just brand`)
│   ├── concepts/
│   ├── banners/
│   ├── social/

│   ├── manifesto/
│   ├── method/

```

**Note on `_source/` naming.** The underscore prefix distinguishes source files from the consumed brand surface (BRAND.md, BIOS.md, etc., which are at the top level). When an Adobe Illustrator export lands in `brand/exports/`, having sources under `_source/` makes the structural distinction (source-vs-derived) obvious at a glance.

## Conventions

### Filenames

- **kebab-case** for all file and directory names: `manifesto.html`, `code-of-conduct.md` (the standard exception is convention-required uppercase: `README.md`, `CONTRIBUTING.md`, `SECURITY.md`, `LICENSE`).
- **Markdown brand docs are uppercase** (BRAND.md, COPY.md, etc.) to mirror repo-root conventions and signal "spec-grade" register.
- **Asset filenames prefix with the product slug**: `facet-readme-dark.webp`, `facet-gem-on-light.svg`. Prevents confusion if assets get loose from their folder.
- **Theme variants** use suffix `-dark` / `-light` (e.g., `manifesto-dark`, `manifesto-light`).
- **Aspect/size variants** when needed: `gem-1200.png` (1200px wide), `lockup-2000.png` (2000px wide).

### What goes in `icons/svg/` vs `icons/png/`

- SVGs are the **canonical source**. Edit / version SVGs; render PNGs from them.
- PNGs are **high-res raster exports** for use cases that don't accept SVG (some social platforms, app stores, OS-level icons). Render at ≥1200px wide for press grade.
- Don't put rasters in `icons/svg/` and don't put vector source in `icons/png/`.

### What goes in `_source/html/` vs `exports/`

- `_source/html/` is **HTML source** — versioned, edited by hand, hot-reloadable in a browser. Each sheet contains all variants (e.g., `manifesto.html` has both `#manifesto-dark` and `#manifesto-light` IDs).
- `_source/ai/` is **Adobe Illustrator source** — `.ai` files for hero illustrations, mascots, vector marks. Editor opens `.ai`, exports to `.svg` or `.webp` in `brand/exports/`.
- `exports/` is **rendered output** — generated by `just brand` (HTML sources via Playwright) AND/OR by Illustrator's Export-As (AI sources). Never edited by hand. Pipeline-rendered files can be regenerated from `_source/html/` at any time; Illustrator-exported files are regenerated from `_source/ai/` via the design tool.

**Cleanup safety.** Because `exports/` mixes pipeline renders and AI exports (both can share the `{{PRODUCT_SLUG}}-*` prefix), the `brand-clean` recipes must enumerate the specific files each `brand-{cat}` render produces — not `rm -rf` whole category directories. See the justfile template for the per-category clean recipe pattern; AI exports survive cleanup.

### What goes in `press/` vs `exports/` and `icons/`

- `press/` is a **self-contained subset** for journalists and partners. Copies of canonical assets (not the canonical sources themselves).
- The press kit's `logos/` are *copies* of `icons/svg/` and high-res PNG renders.
- The press kit's `hero/` are *copies* of `exports/readme/`.
- Self-containment matters because journalists download `press/` as a folder, expecting everything to be there. Symlinks or path references break that expectation.

### Optional extensions

These show up in mature brand libraries — not required at first but worth knowing:

- `brand/_source/html/_archive/` — retired sheets preserved for reference (e.g., a deprecated concept). Don't delete; archive.
- `brand/exports/{type}/thumbs/` — 800px-wide WebP thumbnails alongside full-size 1600px versions. Useful for indexes, README thumbnail grids, IDE previews.
- `brand/exports/composite/` — contact-sheet-style composite images showing all variants in a category at a glance. Useful as a brand library overview image.
- `brand/_source/html/composite.html` — source for the composite reference sheets above.
- `brand/_source/figma/` — if Figma plugin exports are part of the source flow (e.g., Figma → SVG export script), they land here.
- `brand/templates/` — if the product has output templates that carry brand styling (resume templates, email templates, doc templates), they live here.

### When to extend

The structure above is the canonical default. Add subdirectories when there's a real distinction to encode:

- A new **asset type** that doesn't fit existing categories → new `brand/exports/{type}/` subdirectory plus matching `brand/_source/html/{type}.html`. Add a `brand-clean-{type}` companion recipe to the justfile so cleanup stays scoped.
- A separate **brand surface** for a sub-product or partner integration → consider `brand/{sub-brand}/` mirroring the top-level structure.
- **Generated previews / mockups** of brand assets in product UI contexts → `brand/mockups/`.

Don't over-organize. A brand library with 30 subdirectories where 5 would do is harder to maintain than one with the canonical structure.

## File naming for assets

The justfile recipes assume a consistent naming convention. If you change the conventions, update the justfile recipes correspondingly.

## Where decisions.md lives

`brand/decisions.md` is the Phase 0 output — the captured commitments (product name, brand verb, license, pricing model, etc.). It lives in `brand/` rather than the repo root because it's brand-context, not repo-context. Subsequent phases reference `brand/decisions.md` for product-specific values.

If `decisions.md` gets out of sync with the canonical brand docs (BRAND.md / COPY.md / MANIFESTO.md), prefer the canonical doc and update `decisions.md` to match.

## Cross-doc anchor: BRAND.md inventory tree

`brand/BRAND.md` includes its own inventory tree as a navigational aid. Keep that tree updated when adding new files — it's the human-readable map of the library. Verify cross-link integrity per `cross-link-map.md`.
